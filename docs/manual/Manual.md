# AgentStudio 에이전트 빌더 매뉴얼

이 문서는 AgentStudio의 **에이전트 빌더 페이지**(`/agents/[agentId]`) 사용 방법을 화면별로 설명합니다.
각 항목은 **의미 → 사용 예시 → 주의** 순서로 정리되어 있습니다.

> 캡쳐 자리(`![](screenshots/...png)`)는 별도 캡쳐 가이드(`screenshot-checklist.md`)에 따라 추후 채워집니다.

---

## 0. 페이지 전체 구조

에이전트 빌더 페이지는 **상단 툴바 + 좌측 그래프 캔버스 + 우측 패널** 3분할 구조입니다.

- **툴바**: 에이전트 식별, 저장/실행 액션
- **그래프 캔버스**: Main Agent 와 Sub Agent 의 위임 관계를 시각적으로 설계
- **우측 패널**: 두 가지 모드를 토글
  - `설정` 모드: 선택한 노드의 설정값 편집(7개 탭)
  - `디버그` 모드: 실행 중 또는 실행 후 채팅·로그·메트릭 확인(5개 탭)

---

# A. 툴바

![](screenshots/01-toolbar-clean.png)

## A-1. 뒤로가기(`← Agents`)

- **의미**: 에이전트 목록 페이지로 이동합니다(`router.back()`).
- **사용 예시**: 편집을 끝내고 다른 에이전트를 고르고 싶을 때.
- **주의**: 미저장 변경(`미저장` 뱃지가 노란색으로 표시되는 상태)이 있을 때는 저장하고 나가는 것을 권장합니다. 페이지를 떠나면 변경 사항은 자동으로 저장되지 않습니다.

## A-2. 에이전트 이름 표시

- **의미**: 현재 편집 중인 에이전트 이름을 보여줍니다. 이름은 우측 패널 `기본` 탭이나 `Main Agent` 모달에서 변경합니다.
- **사용 예시**: 동일 화면에서 어떤 에이전트를 다루고 있는지 빠르게 확인.
- **주의**: 이름은 단순 라벨이 아니라 시스템 프롬프트와 위임(handoff) 호출에 사용되므로 **공백·특수문자**는 자제. 백엔드에서 자동 sanitize 되지만 의도하지 않은 형태로 표기될 수 있습니다.

## A-3. `미저장` 뱃지

- **의미**: 어떤 설정값을 변경했지만 아직 저장 버튼을 누르지 않은 상태임을 알립니다.
- **사용 예시**: 여러 탭을 옮겨다니며 작업하다가 깜빡 잊고 나가지 않도록 시각적 알림.
- **주의**: 이 뱃지가 보이는 동안 페이지를 새로 고치거나 다른 페이지로 이동하면 변경이 사라집니다.

![](screenshots/02-toolbar-dirty.png)

## A-4. `Main Agent` 버튼

- **의미**: Main Agent 의 핵심 4종 설정(이름, 설명, 아키텍처, Brain Model)만 빠르게 편집하는 모달을 엽니다.
- **사용 예시**: 새 에이전트 만들고 가장 먼저 이름·아키텍처를 정할 때.
- **주의**: 모달은 위 4가지만 다룹니다. 나머지(프롬프트, 도구, 가드레일 등)는 캔버스에서 Main Agent 노드를 클릭한 뒤 우측 설정 패널에서 변경합니다.

## A-5. `실행` 버튼

- **의미**: 디버그 패널을 열고 새 대화 세션을 시작합니다. 만약 미저장 변경이 있으면 **자동으로 먼저 저장**한 뒤 실행합니다.
- **사용 예시**:
  - 프롬프트나 도구 설정을 바꾼 직후 곧바로 테스트하고 싶을 때 → 저장 누를 필요 없이 실행만 누르면 됨.
  - 이전 대화가 남아있어도 실행을 누르면 새 세션으로 초기화됩니다.
- **주의**:
  - 저장이 실패하면(네트워크/검증 오류) 실행이 중단되고 토스트로 오류가 표시됩니다.
  - 실행 중에는 그래프 캔버스가 비활성화되어 노드/엣지를 클릭해도 디버그 패널이 닫히지 않습니다. 종료는 디버그 패널 우측 상단 `X` 버튼으로 합니다.

## A-6. `저장` 버튼

- **의미**: 현재 미저장 변경을 서버(`PUT /agents/:id`)로 전송합니다. 그래프(캔버스 노드 위치 포함)도 함께 저장됩니다.
- **사용 예시**: 실행 없이 설정만 갱신하고 싶을 때.
- **주의**: 미저장 변경이 없으면 비활성(회색) 상태입니다. 저장 중에는 스피너가 표시됩니다.

# B. 그래프 캔버스

![](screenshots/04-canvas-overview.png)

캔버스는 Main Agent 1개와 0개 이상의 Sub Agent로 구성됩니다. 노드 사이 엣지(연결선)는 위임(`task` 도구) 가능한 흐름을 의미합니다.

## B-1. Main Agent 노드

- **의미**: 사용자의 요청을 가장 먼저 받는 메인 에이전트. 사용자가 보내는 메시지는 항상 Main Agent로 전달되고, Main Agent가 직접 답하거나 Sub Agent에게 위임합니다.
- **사용 예시**: 라우팅/감독 역할(supervisor). 도메인 지식이 필요하면 적절한 Sub Agent를 선택해 위임.
- **주의**:
  - Main Agent 노드는 삭제할 수 없습니다.
  - 배지 색상은 아키텍처를 나타냅니다 — 파랑(Deep Autonomous), 초록(Fast), 보라(Planning), 노랑(Custom Graph).

## B-2. Sub Agent 노드

- **의미**: Main Agent가 위임할 수 있는 도메인 특화 에이전트. 각 노드는 독립적인 시스템 프롬프트, 모델, 도구 권한을 가집니다.
- **사용 예시**: `Mail Reader Sub Agent`(메일 검색·요약 전담), `Researcher`(웹 조사 전담), `Writer`(글쓰기 전담) 등 역할 분리.
- **주의**:
  - Sub Agent 이름은 백엔드에서 도구 이름(`agent_<name>`)으로 노출되므로 **공백·이모지·특수문자는 자동 sanitize** 됩니다.
  - 노드 우측 상단 `X` 버튼을 누르면 노드와 연결된 엣지가 삭제됩니다(저장 시 반영).

## B-3. 엣지(연결선)

- **의미**: 에이전트 간 위임 가능성을 표시합니다. Main → Sub 방향이 일반적이며, deepagents는 모든 sub-agent를 main의 flat 자식으로 등록하지만 엣지 정보는 main 시스템 프롬프트에 워크플로우 힌트로 주입됩니다.
- **사용 예시**: `Main → Coordinator → Researcher / Writer` 같은 다단계 흐름을 시각적으로 설계.
- **주의**:
  - 엣지를 클릭하면 삭제됩니다.
  - 실행 중에는 활성 흐름 엣지가 파란색으로 강조되고, 사용되지 않는 엣지는 dim 처리됩니다. 실행 중 엣지 클릭은 비활성화되어 있습니다.

## B-4. `+ Sub Agent 추가` 버튼

- **의미**: 새 Sub Agent 노드를 캔버스에 추가합니다. 현재 선택된 노드가 source가 되어 자동으로 엣지가 그어집니다.
- **사용 예시**:
  - 아무 것도 선택 안 한 상태로 누르면 → Main 에서 이어지는 새 Sub Agent 생성
  - Sub Agent 노드를 선택한 상태로 누르면 → 그 Sub Agent 에서 이어지는 손자 Sub Agent 생성(시각적 표시일 뿐, 실제 위임 흐름은 main 프롬프트로 힌트 주입됨)
- **주의**: 새 Sub Agent 이름은 자동으로 `Sub Agent 1`, `Sub Agent 2` 식으로 부여됩니다. 곧바로 노드를 클릭해 의미 있는 이름으로 바꾸는 것을 권장합니다.

## B-5. 줌/팬 컨트롤(좌측 하단)

- **의미**: ReactFlow 기본 컨트롤 — `+`/`−`/`Fit`/`Lock` 4종.
- **사용 예시**: 노드가 많아져 화면을 벗어나면 `Fit` 버튼으로 한 번에 보기.
- **주의**: 노드 위치는 저장 시 `graphDefinition`에 함께 저장됩니다. 화면을 옮기면 다음에 페이지를 열었을 때 같은 위치에서 시작합니다.

# C. 설정 패널 — Main Agent

![](screenshots/05-canvas-main-selected.png)

Main Agent 노드를 클릭하면 우측에 7개 탭이 있는 설정 패널이 열립니다.

## C-1. `기본` 탭

![](screenshots/10-settings-main-basic.png)

### Agent Name
- **의미**: 에이전트 표시 이름. 시스템 프롬프트와 위임 호출에 사용됩니다.
- **사용 예시**: `customer-support-agent`, `mail-reader` 등 역할이 드러나는 짧은 이름.
- **주의**: 빈 값은 저장되지 않습니다(필수).

### Working Method (Architecture)
4가지 동작 방식 중 하나를 선택합니다.

| 옵션 | 의미 | 권장 사용 |
|---|---|---|
| **Deep Autonomous Agent** | LangChain `deepagents` 패키지 기반. 메모리·계획·서브에이전트·HITL 등 풀 기능을 자동으로 활용. | 복잡한 다단계 작업, Sub Agent 위임이 필요한 경우 |
| **빠른 도구 사용 (Fast)** | 단일 LLM이 즉시 도구를 호출. 계획 단계 없음. | "현재 시각 알려줘" 같은 1턴 도구 호출 |
| **계획 및 실행 (Planning)** | LLM이 먼저 단계 계획을 세운 뒤 하나씩 수행. | 절차가 명확하지만 호출 수가 여러 단계인 작업 |
| **커스텀 그래프 (Expert)** | LangGraph로 직접 그래프 정의(워크플로우 v1). | 조건 분기·루프가 복잡한 경우 |

- **사용 예시**: 메일 분석 후 답장 초안까지 작성하는 에이전트는 `Deep Autonomous`. 단순 검색만 하면 `Fast`.
- **주의**:
  - 가드레일 탭의 일부 기능(`DEEPAGENT 조건` 뱃지 항목)은 Deep Autonomous 에서만 동작합니다.
  - 이미 멀티 아키텍처(`architectures` 배열에 2개 이상)인 경우 카드 선택이 비활성화되며, 변경하려면 별도 플래닝 탭에서 설정해야 합니다.

### Brain Model
- **의미**: 에이전트가 사용하는 LLM. 프로젝트의 Provider 설정에 등록된 모델만 노출됩니다.
- **사용 예시**: 정확도 우선 → `gpt-4o`, `claude-opus-4-7`. 속도 우선 → `gpt-4o-mini`, `claude-haiku-4-5`.
- **주의**: Sub Agent 의 Brain Model 이 비어 있으면 Main Agent 의 모델을 그대로 상속합니다(공백 fallback).

### Purpose (Description)
- **의미**: 에이전트의 역할/시나리오 설명. 사람이 식별하기 위한 메모이며, 사용자가 명시적으로 시스템 프롬프트에 포함시키지 않으면 LLM에 전달되지 않습니다.
- **사용 예시**: "회사 메일을 검색하고 입사 관련 메일을 추려서 요약하는 에이전트"
- **주의**: 빈 값이어도 저장됩니다.

## C-2. `프롬프트` 탭

![](screenshots/11-settings-main-prompt.png)

### 의미
시스템 프롬프트를 블록 단위로 작성·재사용·관리하는 탭입니다. 텍스트/조건/루프 같은 블록 타입을 조합하고, `{{변수}}` 형태의 변수를 끼워 넣을 수 있습니다.

### 사용 예시
- 텍스트 블록: "당신은 사내 메일을 다루는 어시스턴트입니다."
- 조건 블록: 사용자 권한이 admin이면 추가 도구 안내, 아니면 제한된 도구만 안내.
- 변수: `{{user.name}}`, `{{plan.mode}}` 같이 런타임 컨텍스트 주입.

### 주의
- 시스템 프롬프트에 **언어 지정이 없으면 자동으로 한국어 응답** 지시가 추가됩니다(`deepagent_bridge._KOREAN_INSTRUCTION`).
- 길이가 너무 길면 토큰 비용·응답 속도에 영향을 줍니다.

## C-3. `도구` 탭

![](screenshots/12-settings-main-tools.png)

이 탭은 4개 섹션으로 나뉩니다.

### DeepAgents Built-in Tools
- **의미**: deepagents가 기본으로 제공하는 내장 도구. 예: `write_todos`(계획 수립), 가상 파일시스템(VFS) 도구 등.
- **사용 예시**: 다단계 작업에서 plan을 세워 단계별로 진행하고 싶다면 `write_todos` 활성화.
- **주의**: VFS 관련 도구는 현재 비활성화 상태(STATE 탭 UI 구현 후 재활성화 예정).

### Teammates (Sub-agents)
- **의미**: 같은 프로젝트에 있는 다른 에이전트를 sub-agent 로 끌어와 사용. 캔버스에 정의한 Sub Agent 외에도, 별도로 만들어 둔 다른 에이전트를 위임 대상으로 사용 가능.
- **사용 예시**: 이미 잘 만들어둔 `Researcher` 에이전트를 새 `Coordinator` 에이전트에 팀메이트로 추가.
- **주의**: Main Agent 탭에서만 노출됩니다(`hideTeammates` 플래그가 Main 외에는 ON).

### Custom Tools
- **의미**: 프로젝트에 등록된 HTTP/Code/Search 도구. 그룹 단위 또는 개별 단위로 토글합니다.
- **사용 예시**: 사내 API 호출 도구(`gmail_search`)를 추가하면 에이전트가 메일 검색 가능.
- **주의**: 그룹을 클릭하면 해당 그룹의 모든 도구가 동시에 ON/OFF 됩니다. 개별 토글은 그룹을 펼친 뒤 선택.

### MCP Servers
- **의미**: Model Context Protocol(MCP) 서버 단위로 도구 묶음을 추가. 각 서버 안의 개별 툴도 펼쳐서 토글 가능.
- **사용 예시**: 사내 Gmail MCP 서버 등록 후 그 서버의 검색·발송 도구를 모두 활용.
- **주의**: MCP 서버가 죽어 있으면 도구 호출이 실패합니다. 운영 환경에서는 헬스체크와 자동 재시작 권장.

### 주의(공통)
- 활성화한 도구의 권한 정책(읽기/쓰기/HITL 필요 등)은 별도 `도구 권한` 패널 또는 가드레일 설정으로 제어합니다.
- Sub Agent 가 Main 에서 활성화되지 않은 도구를 사용할 수는 있지만, **Main 도구 목록과 Sub 도구 목록은 독립적**입니다.

## C-4. `모델` 탭

![](screenshots/13-settings-main-model.png)

### Brain Model
- **의미**: 기본 탭과 동일. 모델을 변경하면 즉시 반영됩니다(저장 후).
- **사용 예시**: 처음에 큰 모델로 만들고, 비용이 부담되면 작은 모델로 다운그레이드.
- **주의**: 모델 마이그레이션 시 응답 품질이 달라질 수 있어 가드레일·프롬프트 재검토 권장.

### Temperature (0 ~ 2)
- **의미**: 응답의 창의성/무작위성. 0에 가까우면 동일 입력에 대해 거의 같은 답을, 2에 가까우면 변동이 큰 답을 생성합니다.
- **사용 예시**:
  - 분류·추출 등 재현성이 중요한 작업: 0 ~ 0.2
  - 일반 대화: 0.6 ~ 0.9
  - 브레인스토밍·창작: 1.0 ~ 1.5
- **주의**: 너무 높으면 형식이 깨지거나 hallucination 이 늘 수 있습니다.

### Max Tokens (256 ~ 32,768)
- **의미**: 한 응답에서 모델이 출력할 수 있는 최대 토큰 수.
- **사용 예시**: 짧은 답이면 1,024로 제한해 비용 절감, 긴 리포트가 필요하면 8,192 이상.
- **주의**: 모델별로 실제 상한이 다릅니다(예: 일부 모델은 8K 또는 16K). 상한을 넘으면 모델 측에서 잘립니다.

## C-5. `I/O` 탭 (Output Schema)

![](screenshots/14-settings-main-io.png)

### Plain Text / JSON Schema 토글
- **의미**: 에이전트의 최종 응답 형식을 자유 텍스트로 둘지, JSON Schema 로 강제할지 선택합니다.
- **사용 예시**:
  - 사람에게 보여주는 챗봇: `Plain Text`
  - 다운스트림 시스템에 결과를 전달하는 자동화: `JSON Schema` 로 응답 구조 고정
- **주의**: JSON Schema 를 켰는데 가드레일의 `JSON Validation` 도 함께 켜야 실제로 검증·차단이 동작합니다.

### 템플릿
`자유 텍스트` / `분류 결과` / `구조화된 리포트` 3종 템플릿을 클릭 한 번으로 적용합니다.

- **의미**: 자주 쓰는 출력 스키마를 빠르게 시작.
- **사용 예시**: 분류 결과(`category` + `confidence` + `reasoning`) 가 필요한 경우 그 템플릿으로 시작 후 필드 추가.
- **주의**: 템플릿은 시작점일 뿐 — 실제 사용 사례에 맞게 `required` 와 필드를 조정해야 합니다.

### Monaco 에디터
- **의미**: JSON Schema 본문을 직접 편집. 문법 오류는 빨간 표시로 안내됩니다.
- **사용 예시**: `properties`, `required`, `enum`, `minimum/maximum` 등 표준 JSON Schema 키워드 사용.
- **주의**: 잘못된 JSON 이면 자동 저장이 일시적으로 멈춥니다. 오류 문구를 보고 수정하면 됩니다.

## C-6. `가드레일` 탭

![](screenshots/15-settings-main-guardrails.png)

### Safety Level (Low / Med / High)
- **의미**: 안전 강도 메타데이터(`low`/`medium`/`high`). 라벨로 저장됩니다.
- **사용 예시**: 외부 사용자 노출 → High, 내부 데모 → Low.
- **주의**: 현재는 라벨일 뿐, 백엔드에서 자동으로 분기 동작하지 않습니다. 실제 차단·필터를 원하면 아래 항목들을 직접 켜야 합니다.

### 금지 주제 (`blocked_topics`) — DEEPAGENT 조건
- **의미**: 사용자 입력에 등록 키워드가 포함되면 **실행 자체를 거부**합니다. (`InputGuardrail.check`)
- **사용 예시**: 사내 비밀번호/주민번호/대외비 키워드 입력을 차단.
- **주의**: 부분 문자열 매칭(소문자 비교)이라 `password` 등록 시 `passwordless` 도 차단됩니다. 필요하면 출력 필터에 정규식으로 정밀화.

### 출력 필터 규칙 (`output_filters`) — DEEPAGENT 조건
세 가지 필터 타입을 지원합니다(현재 `keyword`/`regex`는 동일하게 정규식으로 처리).

| 필터 타입 | 설명 |
|---|---|
| `Keyword` | 단순 문자열로 입력하지만 백엔드는 정규식으로 처리. `.`, `*` 등 메타문자는 이스케이프 필요 |
| `Regex` | 정규식 직접 입력 |
| `LLM Check` | 별도 LLM 호출로 위반 여부 판정(현 버전에서는 미구현, 라벨만 저장) |

액션은 `Block` / `Mask` / `Warn` 3가지지만, 현재 백엔드는 매칭된 부분을 `[FILTERED]`로 교체하는 동작만 수행합니다.

- **사용 예시**: 응답에 신용카드 번호 패턴이 들어가면 마스킹 → `\b(?:\d[ -]?){13,16}\b` 정규식 등록.
- **주의**: 정규식이 너무 광범위하면 정상 응답까지 가려질 수 있습니다. 테스트 후 적용.

### JSON Validation
- **의미**: I/O 탭에서 정의한 JSON Schema 로 응답을 검증. 실패하면 검증 오류 사유 반환.
- **사용 예시**: 다운스트림 시스템이 특정 필드(`category`, `confidence`)를 반드시 필요로 할 때.
- **주의**: 토글만 켜고 `outputSchema` 가 비어 있으면 동작하지 않습니다.

### PII Masking — DEEPAGENT 조건
- **의미**: 응답 텍스트에서 이메일·전화번호·주민번호·신용카드·SSN·IP 같은 개인정보를 자동으로 `[REDACTED]` 처리.
- **사용 예시**: 외부 메일 본문을 요약할 때 응답에 메일 주소가 그대로 남는 것을 방지.
- **주의**: 정규식 기반이라 비표준 포맷(공백·하이픈 변형)은 놓칠 수 있습니다. 민감한 환경에선 추가 출력 필터로 보완.

### Max Output Tokens (100 ~ 8,000)
- **의미**: 가드레일 차원의 최종 출력 토큰 상한. 모델 탭의 `Max Tokens` 와 별개로 한 번 더 짧게 제한할 때 사용.
- **사용 예시**: 모델 자체는 4,000 토큰 출력 가능하지만, 챗봇 UX 에선 1,000 으로 제한해 응답을 짧게.
- **주의**: 모델 탭 값보다 크게 설정해도 의미가 없습니다(작은 값이 우선).

## C-7. `HANDOFF` 탭

![](screenshots/16-settings-main-handoff.png)

### 핸드오프 조건 (`handoffCondition`)
- **의미**: 어떤 상황에서 다른 에이전트로 대화를 넘길지 자연어로 기술합니다.
- **사용 예시**: "결제 환불 문의가 들어오면 billing-agent 로 핸드오프"
- **주의**: 텍스트는 시스템 프롬프트 일부로 모델에 전달됩니다. 너무 모호하면 항상 핸드오프하거나 절대 핸드오프하지 않을 수 있어 구체적으로 기술.

### 대상 에이전트 (`handoffTarget`)
- **의미**: 핸드오프 시 전환될 에이전트의 ID.
- **사용 예시**: Sub Agent 가 추가된 후 셀렉터에서 선택.
- **주의**: 현재 빌드는 셀렉터에 비어 있는 옵션만 노출됩니다(추가 구현 예정). 임시로 비워둬도 무방.

# D. 설정 패널 — Sub Agent

![](screenshots/06-canvas-sub-selected.png)

Sub Agent 노드를 클릭하면 동일한 7개 탭(`기본` / `프롬프트` / `도구` / `모델` / `I/O` / `가드레일` / `HANDOFF`)이 표시됩니다. 동작은 Main Agent 와 같지만 몇 가지 차이가 있습니다.

## D-1. Main 과 동일한 항목

- 프롬프트, 모델, I/O(Output Schema), 가드레일, HANDOFF 는 Main 과 같은 화면·동작입니다.
- **사용 예시**: Sub Agent 마다 다른 시스템 프롬프트와 도구를 부여해 역할을 분리.
- **주의**: 가드레일도 Sub Agent 별로 따로 설정됩니다. 민감 정보가 Sub Agent 응답에서만 새는 것을 방지하려면 PII Masking 도 그쪽에 켜야 합니다.

## D-2. Main 과 다른 항목

### `도구` 탭의 Teammates 섹션 — 미노출
- Main 에서만 다른 에이전트를 팀메이트로 추가할 수 있습니다. Sub Agent 에서는 이 섹션이 숨겨져 있습니다(`hideTeammates`).

### `기본` 탭의 Architecture
- Sub Agent 는 일반적으로 **Deep Autonomous** 또는 **Fast** 만 사용하는 것이 자연스럽습니다(서브 단계에서 또 다른 plan_execute 를 두는 것은 권장하지 않음).

### Brain Model 빈 값
- Sub Agent 의 모델을 지정하지 않으면 Main 모델을 상속합니다.
- **주의**: 모델 키가 다른 Provider(예: Anthropic) 인데 Provider 등록이 안 되어 있으면 실행 시 RuntimeError 가 납니다.

# F. 디버그 패널

![](screenshots/40-debug-empty.png)

`실행` 버튼을 누르면 우측에 표시되는 패널입니다. 5개 탭(`채팅` / `실행 로그` / `메트릭` / `RAW` / `경고`)과 채팅 입력창을 제공합니다.

## F-1. 패널 헤더
- **의미**: 좌측에 패널 이름, 우측에 두 개 액션 — `↻`(초기화), `X`(닫기).
- **사용 예시**:
  - `↻`: 같은 세션에서 그동안 쌓인 채팅·로그·메트릭을 모두 비우고 새로 시작
  - `X`: 디버그 패널 닫기 + 실행 종료(`isRunning=false`)
- **주의**: `X` 로 닫으면 진행 중이던 요청도 중단(abort)됩니다.

## F-2. `채팅` 탭

![](screenshots/42-debug-chat-completed.png)

기본 화면. 사용자 메시지·AI 응답 외에 다음 카드들이 함께 표시됩니다.

### 메시지 버블
- **의미**: 사용자(`U`) 메시지는 우측 파랑, AI 메시지는 좌측 어두운 버블.
- **사용 예시**: 일반 채팅 인터페이스와 동일.
- **주의**: AI 메시지는 스트리밍 중에는 한 글자씩 채워지고, 완료 시 `streaming: false` 로 고정됩니다.

### 사고 카드(Thinking)
- **의미**: 모델의 reasoning 내용. 기본 접힘 상태이며 클릭으로 펼치면 전체 사고 과정 확인 가능.
- **사용 예시**: 왜 이 도구를 골랐는지 디버깅.
- **주의**: 모든 모델이 reasoning 을 내보내지는 않습니다. 일부 모델·설정에서는 보이지 않을 수 있습니다.

### 도구 호출 카드(Tool Call)
- **의미**: 도구 한 번 호출에 대응하는 카드. 입력(Input)·출력(Output)·소요 시간(ms)·완료 뱃지를 표시. 서브 에이전트 호출은 파랑 테두리, 일반 도구는 흰 테두리.
- **사용 예시**: `gmail_search` 호출이 어떤 인자로 이루어졌고 어떤 결과를 반환했는지 확인.
- **주의**: 호출 직후엔 노란색(진행 중), 완료 시 초록색, 실패 시 빨간색으로 색상이 바뀝니다.

### Todo List 카드
- **의미**: `write_todos` 도구 호출 결과로 만들어진 단계별 계획. `pending` → `in_progress` → `completed` 로 단계가 진행될 때마다 카드가 갱신됩니다.
- **사용 예시**: 다단계 작업이 어디까지 진행됐는지 한눈에 확인.
- **주의**: 에이전트가 `write_todos` 를 한 번도 호출하지 않으면 카드가 표시되지 않습니다.

### HITL 승인 카드

![](screenshots/43-debug-chat-hitl-request.png)

- **의미**: 가드레일 또는 도구 정책에 의해 사용자 승인이 필요한 도구 호출이 발생하면 표시. 도구명을 한국어 표시명으로(예: `gmail_search` → "Gmail 검색"), 인자를 레이블 있는 리스트(예: 검색어 / 최대 결과 개수 등)로 풀어서 보여줍니다.
- **사용 예시**: 사용자가 "메일 보내줘" 라고 하면 `gmail_send` 가 자동으로 발송되지 않고, 본문/수신자가 의도와 맞는지 확인 후 `허용` 누르도록.
- **주의**:
  - 카드의 `거부` / `수정` / `허용` 버튼은 백엔드 정책(`allowedDecisions`)에 따라 일부만 노출됩니다.
  - `수정` 을 누르면 인라인 편집 폼이 펼쳐집니다(아래).

![](screenshots/44-debug-chat-hitl-edit.png)

- **인라인 편집 폼**: 각 인자별 입력 필드와 타입 힌트(예/아니오, 숫자, JSON 형식)가 표시됩니다.
- **사용 예시**: 검색어를 다듬어 더 정확한 결과를 받고 싶을 때 → "검색어" 필드 수정 후 "수정하고 실행".
- **주의**:
  - 숫자/불리언/객체는 자동 파싱됩니다(잘못 입력하면 원래 값 유지).
  - "취소" 를 눌러도 기존 카드 상태로 돌아갈 뿐, 도구 호출이 중단되지는 않습니다(승인/거부 중 하나를 선택해야 진행).

## F-3. `실행 로그` 탭

![](screenshots/45-debug-log.png)

- **의미**: 모든 단계(step)의 시작·완료·실패 이벤트를 시간 순으로 텍스트 로그로 표시.
- **사용 예시**: 채팅 카드에서 도구 카드가 너무 많을 때, 시간 라벨로 빠르게 흐름 파악.
- **주의**: 레벨은 INFO/DONE/WARN/ERROR 4종. ERROR 가 보이면 `경고` 탭에도 동일 항목이 추가됩니다.

## F-4. `메트릭` 탭

![](screenshots/46-debug-metrics.png)

- **의미**: 입력 토큰 / 출력 토큰 / 응답 시간 / 비용 4가지 카드.
- **사용 예시**: 한 턴이 얼마나 비싼지, 얼마나 오래 걸렸는지 빠른 확인.
- **주의**:
  - 비용은 Provider 단가표 기반 추정치입니다. 실제 청구액과 차이 가능.
  - 응답 시간은 모든 단계 latency 의 합계입니다(병렬 호출 포함).

## F-5. `RAW` 탭

![](screenshots/47-debug-raw.png)

- **의미**: 각 노드(step)의 원본 출력 JSON. 가드레일 통과 후의 가공된 텍스트가 아니라 모델/도구 원본을 보여줍니다.
- **사용 예시**: 채팅 카드에 안 보이는 메타데이터(usage·model·tool_use_id 등)를 확인할 때.
- **주의**: 길이가 매우 길 수 있습니다. 검색은 브라우저의 `Cmd+F` 사용.

## F-6. `경고` 탭

![](screenshots/48-debug-warnings.png)

- **의미**: 실행 중 발생한 ERROR 레벨 이벤트만 모아서 표시. 탭 라벨 옆에 카운트 뱃지.
- **사용 예시**: HITL middleware 알림성 메시지처럼 사용자가 빠르게 검토해야 하는 항목.
- **주의**: 빈 상태에서는 "경고 없음" 이 표시됩니다.

## F-7. 채팅 입력창

![](screenshots/49-debug-input.png)

- **의미**: 패널 하단의 textarea + 전송 버튼.
- **사용 예시**:
  - 메시지 입력 후 `Ctrl+Enter` (mac은 `Cmd+Enter`)로 전송.
  - 마우스로 우측 ▶ 버튼 클릭으로도 전송.
- **주의**:
  - 실행 중에는 textarea 가 비활성화되고, 버튼은 스피너로 바뀝니다.
  - 빈 입력으로는 전송되지 않습니다.

# 부록 A. 자주 마주치는 문제

## "실행 후 메시지를 보냈는데 응답이 안 와요"
- 디버그 패널의 `경고` 탭과 `실행 로그` 탭을 먼저 확인합니다.
- 가드레일 `금지 주제` 에 입력 키워드가 걸려 거부되었을 가능성 → 입력 메시지 점검.
- WS 연결이 끊긴 경우 패널을 닫았다가 다시 열어 보세요.

## "Sub Agent 로 위임이 안 일어나요"
- Sub Agent 의 description 이 모호하면 LLM 이 위임 가치를 판단하지 못합니다 → 한 줄로 명확한 역할 기술.
- Main Agent 가 직접 답하기에 충분한 도구를 가지고 있다면 위임이 일어나지 않습니다 → 도구 권한을 분리.

## "JSON Schema 로 강제했는데 응답이 자유 텍스트로 옵니다"
- I/O 탭의 토글이 `Plain Text` 로 되어 있는지 확인.
- 가드레일의 `JSON Validation` 도 같이 켜져 있어야 검증이 동작합니다.
